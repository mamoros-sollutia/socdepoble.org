# 🛡️ PETORRETA RESOLTA: BASE DADES EMPRESA USUARI

## 1. SCRIPT SQL — PURGA DE PERFILS ZOMBIS

### Per què van quedar orfes?
Supabase crea el perfil a `public.profiles` mitjançant un trigger (`on_auth_user_created`) quan s'insereix un usuari a `auth.users`. **Però no existeix el procés invers**: quan s'esborra manualment un usuari des del panell d'Autenticació, la clau forana de `public.profiles.id` → `auth.users.id` **no té `ON DELETE CASCADE`** (Supabase ho impedeix per disseny, ja que `auth` és un esquema protegit). El resultat: registres orfes a `public.profiles` que ja no tenen corresponència a `auth.users`.

### 🔒 SDP-LOCK: Script de neteja segur

**Primer — Verificació (SELECT abans de DELETE):**
```sql
-- Confirma que són exactament 3 i que realment no existeixen a auth.users
SELECT p.id, p.username, p.created_at
FROM public.profiles p
LEFT JOIN auth.users au ON au.id = p.id
WHERE p.username IS NULL
  AND au.id IS NULL;
```

**Segon — Purga controlada:**
```sql
BEGIN;

-- Esborra només els perfils orfes amb username IS NULL
-- La doble condició (username IS NULL + no existir a auth.users)
-- evita esborrar perfils legítims que encara no hagin establert username
DELETE FROM public.profiles
WHERE username IS NULL
  AND id NOT IN (SELECT id FROM auth.users);

-- Confirma quant s'ha esborrat
GET DIAGNOSTICS affected_rows = ROW_COUNT;
RAISE NOTICE 'Perfils esborrats: %', affected_rows;

COMMIT;
```

### Consideracions RLS
- Aquesta operació **s'ha d'executar des del SQL Editor del Supabase Studio amb rol `postgres`** (el Mestre).
- Les polítiques RLS de `public.profiles` no s'apliquen al rol `postgres`, per tant l'operació funcionarà.
- Si hi hagués taules dependents amb claus foranes cap a `profiles.id` (per exemple `projects.profile_id`), caldria afegir `ON DELETE CASCADE` o esborrar primer les dependències. En aquest cas, com que són perfils de prova sense dades associades, no cal.

## 2. ARQUITECTURA — SEPARACIÓ D'IDENTITATS (PERSONA vs ENTITAT)

### 2.1 Model de Base de Dades

#### Taula `public.profiles` (Identitat Personal — 1:1 amb auth.users)
Roman intacta com a fonament de l'autenticació. Representa **una persona física**.

| Camp | Tipus | Descripció |
|------|-------|------------|
| `id` | uuid | FK → `auth.users.id` (PK) |
| `username` | text | Nom d'usuari personal |
| `full_name` | text | Nom complet personal |
| `avatar_url` | text | Avatar personal |
| `personal_data` | jsonb | Dades personals (contacte, preferències, etc.) |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |

#### 🆕 Taula `public.entities` (Identitat d'Empresa/Grup)
Representa **una organització, empresa, associació o col·lectiu**.

| Camp | Tipus | Descripció |
|------|-------|------------|
| `id` | uuid | PK (autogenerada) |
| `slug` | text | Identificador únic (ex: "sollutia", "el-rentonar") |
| `name` | text | Nom oficial de l'entitat |
| `entity_type` | enum | `empresa`, `associacio`, `grup`, `col·lectiu` |
| `description` | text | Descripció pública |
| `avatar_url` | text | Logo/imatge de l'entitat |
| `entity_data` | jsonb | Dades específiques de l'entitat (NIF, contacte, etc.) |
| `created_by` | uuid | FK → `profiles.id` (qui la va crear) |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |

#### 🆕 Taula `public.entity_members` (Relació Persona ↔ Entitat)
Connecta persones amb entitats i defineix el seu rol dins de cadascuna.

| Camp | Tipus | Descripció |
|------|-------|------------|
| `id` | uuid | PK |
| `profile_id` | uuid | FK → `profiles.id` |
| `entity_id` | uuid | FK → `entities.id` |
| `role` | enum | `propietari`, `administrador`, `col·laborador`, `lector` |
| `shared_data_scopes` | jsonb | Quines dades personals es comparteixen amb aquesta entitat (ex: `["email", "telefon"]`) |
| `joined_at` | timestamptz | |
| `created_at` | timestamptz | |

**Restricció única:** `UNIQUE(profile_id, entity_id)` — una persona no pot estar dues vegades a la mateixa entitat.

#### 🆕 Taula `public.entity_data` (Dades pròpies de l'entitat)
Per a dades que pertanyen a l'entitat mateixa (no a la persona).

| Camp | Tipus | Descripció |
|------|-------|------------|
| `id` | uuid | PK |
| `entity_id` | uuid | FK → `entities.id` |
| `data_key` | text | Clau del tipus de dada (ex: "projectes", "facturacio", "equip") |
| `data_value` | jsonb | El contingut |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |

### 2.2 Polítiques RLS

**Per a `entities`:**
- Qualsevol usuari autenticat pot **llegir** entitats on és membre.
- Només `propietari` o `administrador` poden **editar** l'entitat.

**Per a `entity_members`:**
- Un usuari pot veure els seus propis vincles i els de les entitats on administra.
- Només el propietari pot afegir/treure membres.

**Per a `entity_data`:**
- Llegir per a membres de l'entitat.
- Escriure segons rol dins l'entitat.

### 2.3 Arquitectura React — Descomposició de `AppDataContext.jsx`

L'actual context monolític es descompon en **4 sub-contextos especialitzats** que treballen en cascada. L'usuari pot "canviar de somriure" (identitat activa) en qualsevol moment.

```
┌─────────────────────────────────────────────────┐
│              App (root component)               │
│                                                 │
│  ┌───────────────────────────────────────────┐  │
│  │         AuthContext (proveïdor)           │  │
│  │  - usuari autenticat (auth.users)         │  │
│  │  - estat de sessió                        │  │
│  └───────────────────┬───────────────────────┘  │
│                      ↓                          │
│  ┌───────────────────────────────────────────┐  │
│  │        ProfileContext (proveïdor)         │  │
│  │  - perfil personal (public.profiles)      │  │
│  │  - dades personals                        │  │
│  └───────────────────┬───────────────────────┘  │
│                      ↓                          │
│  ┌───────────────────────────────────────────┐  │
│  │        EntityContext (proveïdor)          │  │
│  │  - llista d'entitats on l'usuari pertany  │  │
│  │  - rols per entitat                       │  │
│  │  - dades de cada entitat                  │  │
│  └───────────────────┬───────────────────────┘  │
│                      ↓                          │
│  ┌───────────────────────────────────────────┐  │
│  │     ActiveIdentityContext (proveïdor)     │  │
│  │  - identitat ACTIVA actual (persona o     │  │
│  │    una entitat específica)                │  │
│  │  - "al màxim nivell" → dades disponibles  │  │
│  │    segons el context actiu                │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

#### 2.3.1 `AuthContext.jsx`
```jsx
// Proporciona: user, session, isLoading, signIn, signOut
// Només autenticació GoTrue. Res més.
```

#### 2.3.2 `ProfileContext.jsx`
```jsx
// Proporciona: profile, personalData, updateProfile, updatePersonalData
// Gestiona exclusivament la identitat PERSONAL de l'usuari.
// Les dades personals aquí són "la font de veritat" — l'usuari decideix
// quins camps comparteix amb quines entitats (mitjançant shared_data_scopes).
```

#### 2.3.3 `EntityContext.jsx`
```jsx
// Proporciona:
//   - entities: Array de totes entitats on l'usuari pertany
//   - activeEntity: L'entitat seleccionada actualment (pot ser null)
//   - getEntityData(entityId, key): Obté dades d'una entitat
//   - setEntityData(entityId, key, value): Escriu dades d'entitat
//   - getMembers(entityId): Llista de membres d'una entitat
//   - shareDataWithEntity(entityId, scopes): Configura quines dades
//     personals es comparteixen amb aquesta entitat
```

#### 2.3.4 `ActiveIdentityContext.jsx` — El "canviador"
```jsx
// Proporciona:
//   - activeIdentity: { type: 'persona' | 'entitat', entity: Entity|null }
//   - setActiveIdentity(type, entityId?): Canvia la identitat activa
//   - availableData: Objecte amb les dades disponibles "al màxim nivell"
//     segons la identitat activa:
//       · Si type === 'persona' → dades personals completes
//       · Si type === 'entitat' → {
//           ...dades de l'entitat,
//           ...dades personals de l'usuari que ha compartit amb aquesta entitat
//         }
//   - moveDataToEntity(fromScope, toEntityId, dataKey, dataValue):
//       "Passar dades" de l'Àmbit Personal a una Entitat concreta
//   - moveDataToPersonal(fromEntityId, dataKey):
//       "Tornar a portar" dades d'una Entitat cap a l'Àmbit Personal
```

### 2.4 Flux d'ús: "L'usuari gestiona i passa dades lliurement"

**Exemple: L'usuari vol compartir el seu telèfon amb Sollutia**
1. A `ProfileContext` té `personalData = { telefon: "600000000", email: "...", adreca: "..." }`
2. Crida `entityContext.shareDataWithEntity(entityId_Sollutia, ["telefon", "email"])`
3. Es guarda a `entity_members.shared_data_scopes = ["telefon", "email"]`
4. Quan canvia a identitat activa "Sollutia", `activeIdentityContext.availableData` conté `{ telefon, email }` + totes les dades pròpies de Sollutia

**Exemple: L'usuari vol "passar" un projecte de personal a empresarial**
1. A l'Àmbit Personal té un projecte guardat a `personalData.projectes`
2. Selecciona identitat activa = Sollutia
3. Crida `activeIdentityContext.moveDataToEntity('personal', sollutiaId, 'projecte', {...})`
4. El projecte s'esborra de `personalData.projectes` i s'afegeix a `entity_data` de Sollutia

### 2.5 Hook conveniència: `useActiveData()`

```jsx
// En qualsevol component:
const { data, identityType, switchToPersona, switchToEntity } = useActiveData();

// data sempre conté les dades disponibles "al màxim nivell" segons
// la identitat que tingui activa l'usuari en aquest moment.
// Els components no necessiten saber si venen de persona o entitat.
```

## RESUM

| Qüestió | Solució |
|---------|---------|
| **Perfils zombis** | SQL amb doble condició `username IS NULL` + `NOT IN auth.users`, executat per `postgres` |
| **Causa** | Falta de `ON DELETE CASCADE` entre `auth.users` i `public.profiles` (disseny Supabase) |
| **Model BBDD** | `profiles` (persona) + `entities` (grup/empresa) + `entity_members` (relació amb rol + scopes de compartició) + `entity_data` |
| **React Context** | 4 contextos en cascada: `Auth` → `Profile` → `Entity` → `ActiveIdentity` (el canviador) |
| **Compatibilitat Sollutia** | Sollutia és una `entity` més; l'usuari decideix quines dades personals hi flueixen |

---

> **Tancament de seguretat:** L'script SQL és controlat (BEGIN/COMMIT + SELECT previ de verificació). El model de dades no toca dades personals sense consentiment explícit de l'usuari mitjançant `shared_data_scopes`. No s'afegeixen dependències supèrflues. Arquitectura Online-First respectada.
