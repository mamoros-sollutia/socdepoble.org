## 🔬 ENGINYERIA INVERSA: COM ESTÀ MUNTAT EL SISTEMA

### Visió General
El projecte és una **aplicació web React 18 SPA** construïda amb Vite, que segueix un patró **Online-First** amb **Supabase com a Backend as a Service** (PostgreSQL + GoTrue Auth + RLS + Storage). L'estat es gestiona principalment amb la **Context API** de React en múltiples capes especialitzades.

### Pila Tecnològica Detectada
| Capa | Tecnologia | Observacions |

| Frontend | React 18 + Vite | SPA pur, sense SSR/SSG |

| Navegació | React Router | Rutes per seccions del Mas |

## 💥 DIAGNÓSI HIPERDESTRUCTIVA: FORATS I VULNERABILITATS

### 🚨 CRÍTICS (P0 — RISC DE VIDA DEL SISTEMA)

#### 1. PUNT ÚNIC DE FALLADA: SUPABASE
Tot el sistema depèn d'un **proveïdor BaaS extern** com a espina dorsal única.
- **El problema**: Si Supabase canvia els preus de forma prohibitiva, tanca serveis, pateix una avaria prolongada, o canvia els seus termes de servei, **el Mas cau completament**. No hi ha estratègia de sortida definida ni interfícies d'abstracció que permetin substituir Supabase sense una reescriptura massiva.
- **Evidència**: `supabaseBackend.js` (1002 línies) crida directament `createClient` de Supabase a tot arreu. `backendPort.js` és un adaptador parcial però no aïlla completament.
- **Risc a 5 anys**: Supabase és una empresa startup. La seva supervivència a llarg termini no està garantida. El projecte amarra el seu destí a un tercer.

#### 2. ACOBLAMENT FORT ENTRE CAPES
La lògica de negoci està barrejada íntimament amb els detalls d'infraestructura de Supabase.
- **El problema**: No hi ha una separació clara entre "què fa el sistema" i "com ho fa físicament". Les consultes SQL, la gestió d'autenticació i el format de les taules són coneguts per tota l'aplicació.
- **Conseqüència**: Qualsevol canvi de backend requereix tocar centenars de fitxers. Impossibilita l'adopció futura d'una arquitectura descentralitzada o sobirana.

#### 3. MONOLITISME FRONTAL
Components i fitxers que han crescut de forma incontrolada:
- `App.jsx`: **675 línies** — orquestra tot, massa responsabilitats
- `UniversalElements.jsx`: **795 línies** — barreja molts components diferents
- `DesignSectionContent.jsx`: **1219 línies** — component gegant, difícil de mantindre
- `supabaseBackend.js`: **1002 línies** — tota la capa de dades en un sol fitxer
- `index.css`: **129KB / 3745 línies** — CSS monolític sense modularització
- **El problema**: Violació clara del principi de responsabilitat única. Difícil de testejar, difícil de refactoritzar, fàcil d'introduir regressions.

### ⚠️ ALTS (P1 — DEUTE TÈCNIC GRAU)

#### 4. ESTILS EN LÍNIA ENDÈMICS
**121 fitxers** contenen estils inline `style={{}}`.
- **El problema**: Els estils en línia són impossibles de sobrescriure des de CSS, dificulten el theming, impedeixen la minimització adequada i són un anti-patró React.
- **La "solució" actual**: S'han creat **6 scripts separats** (`scripts/fix_inline_styles1.mjs` fins al `6.mjs`) que fan reemplaços regex per convertir alguns estils en classes. Aquesta és una **parxa temporal fràgil**, no una solució arquitectònica. Un canvi menor en el codi font pot trencar els patrons regex.

#### 5. MANEIG D'ERRORS FEBLE
**9 casos** on els blocs `catch` només registren l'error sense cap estratègia de recuperació:
- `tooling/brain/crear_bundle.mjs`
- `tooling/brain/despertar.mjs` (2 cops)
- `tooling/brain/somiador.mjs` (3 cops)
- `tooling/gates/tancament.mjs` (2 cops)
- `tooling/preflight.mjs`
- **El problema**: Quan alguna cosa falla en l'eixam d'agents, l'error es degrada a un `console.warn` i el sistema continua com si res. Pot portar a inconsistències silencioses en les dades.

#### 6. ACCÉS DIRECTE A DOM GLOBAL
**12 usos** directes de `document.body`, `document.documentElement`, `document.head` des de components React:
- `App.jsx` → `document.body`, `document.documentElement`
- `AppDataContext.jsx` → `document.documentElement`
- `AvisadorEfimer.jsx` → `document.body`
- `useSEO.js` → `document.head`
- **El problema**: Fa els components imposibles de testejar aïlladament, incompatible amb SSR/SSG si mai es vol, i viola l'abstracció de React.

## 🔮 REDISSENY A 5 ANYS VISTA: CAP A LA RESILIÈNCIA TOTAL

### Fase 1: Aïllament i Abstracció (0-12 mesos)
**Objectiu**: Trencar l'acoblament amb Supabase sense canviar el comportament extern.

1. **Arquitectura Hexagonal / Ports & Adapters**
   - Definir interfícies pures per a cada cas d'ús: `NotesRepository`, `PeopleRepository`, `AuthService`, etc.
   - Crear adaptadors per a Supabase que implementin aquestes interfícies.
   - Tot el codi de l'aplicació només coneix les interfícies, mai l'adaptador concret.

2. **Estratègia de Sortida de Supabase**
   - Com a prova de concepte, crear un segon adaptador que funcioni contra un backend simple (Express + PostgreSQL) o fins i tot contra localStorage.
   - Això demostra que l'abstracció funciona i dona la llibertat de canviar quan calga.

3. **Componentització Fina**
   - Descomposar els components gegants: `UniversalElements.jsx` → múltiples fitxers per component.
   - `DesignSectionContent.jsx` → components més petits i composables.
   - `App.jsx` → orquestrador lleuger amb la lògica distribuïda.

### Fase 2: Modernització i Robustesa (12-24 mesos)
1. **Modularització del CSS**
   - Passar de `index.css` monolític a **CSS Modules** per component o a `vanilla-extract`.
   - Els design tokens es defineixen en un sol lloc i s'importen on calguen.
   - Eliminar completament els estils inline (no amb scripts regex, sinó amb refactorització adequada).

2. **Sistema de Build i Qualitat**
   - Afegir **bundle analysis** per vigiljar el pes del build.
   - **Code splitting** per rutes (React Router + lazy loading).
   - **ESLint + regles estrictes** que prohibeixin els estils inline, l'accés directe a document, els literals màgics.
   - **Pre-commit hooks** que executen linting i tests.

3. **Estrategia de Tests Sòlida**
   - Tests unitaris per a cada cas d'ús (la lògica de negoci, aïllada dels adaptadors).
   - Tests d'integració per a cada adaptador.
   - Tests E2E amb Playwright per a les rutes principals.

### Fase 3: Cap a la Sobirania (24-60 mesos)
1. **Desacoblament Progressiu**
   - Si Supabase continua sent viable, mantenir-lo però com a una opció més.
   - Preparar el terreny per a una arquitectura **Local-First progressiva** (CRDTs, sincronització P2P) sense perdre la connectivitat actual.
   - L'objectiu no és abandonar Supabase avui, sinó **no dependre d'ell demà**.

2. **Pipeline CI/CD Complet**
   - Tests automàtics en cada push.
   - Build automàtic.
   - Deploy a staging amb verificacions automàtiques.
   - Deploy a producció només si tot passa.

3. **Simplificació del Maquinari**
   - El sistema d'agents és potent però complex. Documentar-lo exhaustivament i, on siga possible, simplificar-lo o fusionar scripts redundants.
   - Convertir els scripts `fix_*` ad-hoc en regles de linting permanents que impedeixin que el problema torne a sorgir.
