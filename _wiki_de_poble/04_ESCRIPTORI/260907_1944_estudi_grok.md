# Pla tècnic Fase 3: Autenticació, Usuaris, Entitats i Connexió amb Sollutia (Auditoria Grok)

L’arquitectura actual ja està preparada per a Online-First (ADR-2026-08). El frontend té `IdentitatContext` (actor `persona` via `/jo` o `entitat` via `/e/:slug`), `SessionContext`, OAuth relay amb PKCE, `OnboardingSection` de 3 passos i un `supabase/schema.sql` amb `profiles`, `organizations`, `organization_memberships`, `towns` i RLS. El pla reforça i tanca el flux sense reinventar.

### 1. Estat actual rellevant

- **Auth**: `oauthRelay.js` + `public/auth/callback.html` (relé únic `https://auth.socdepoble.org/callback`, PKCE, 3 camins de retorn). `supabaseBackend.js` implementa `registerWithEmail`, `loginWithEmail`, `loginWithGoogle`, `recullTornadaOAuth`, `logout`, `getCurrentUser`.
- **Identitats**: `IdentitatContext` deriva `actorType`/`actorId` de la ruta. Comentari explícit: “En el futur ací es farà un fetch a backend per carregar organizations i organization_memberships”.
- **Onboarding**: 3 passos (personal → empresa → grup). Validacions a `onboardingModel.js`. Crida als mètodes del `backendPort`.
- **Esquema existent** (ja al bundle):
  - `profiles` (1:1 amb `auth.users`, `full_name`, `visibility='private'`, `consentiment_rgpd_at`).
  - `organizations` (tenant_id → towns, kind ∈ {company, group, entity, city_hall}, parent per a groups, slug únic per tenant, created_by).
  - `organization_memberships` (role ∈ {owner, admin, member}, índex d’un sol owner).
  - Trigger `handle_new_user` crea el perfil.
  - Funcions RLS: `private.is_organization_member`, `private.can_manage_organization`, `private.is_town_member`, `private.can_create_group`, protecció del darrer owner (`sdp_protegeix_propietari`).
  - Towns + town_memberships com a tenant.

### 3. Flux de Registre / Autenticació

**A. Registre amb email (camí principal de l’Onboarding)**  
1. `OnboardingSection` → `registerWithEmail({ name, email, password })`.  
2. Supabase Auth crea `auth.users`.  
3. Trigger `handle_new_user` → fila a `profiles` (full_name des de metadata, consentiment_rgpd_at = now()).  
4. Retorn: estat “confirma el correu”. L’usuari confirma → pot fer login.  
5. Després del login: pas 2 (crear organization kind=company/entity) i pas 3 (opcional group).

**B. Login amb email / Google**  
- Email: `loginWithEmail` → desa JWT + refresh a storage efímer + `socdepoble-user`.  
- Google: `loginWithGoogle` → relé PKCE → `recullTornadaOAuth` bescanvia el codi → mateix emmagatzematge.  
- Qualsevol canvi d’auth emet `sdp:auth-change` → `SessionContext` actualitza `currentUser`.

**C. Post-login (Identitat)**  
- `IdentitatProvider` (ampliar):  
  ```js
  // després d’auth
  const orgs = await listMyOrganizations();
  setMemberships(orgs); // { organization_id, slug, role, kind, name, ... }
  ```
- Ruta `/jo` → actorType='persona', actorId=user.id.  
- Ruta `/e/:slug` → comprova que l’usuari té membership amb role ≥ member; si no, 403 o redirect a `/jo`.

**D. Creació d’Entitat**  
- `createOrganization({ name, slug, kind, description, lema, parent_organization_id?, tenant_id })`.  
- Backend: insert a `organizations` + trigger afegeix membership owner.  
- Validació frontend ja existeix a `validateOrganization`.

**E. Reclamació d’Entitat existent**  
- UI nova (o pas opcional a Onboarding): triar organization pública → enviar `entity_claims`.  
- Superadmin (o owner actual) aprova → insert a `organization_memberships` amb role=owner/admin i esborra/marca la claim.

**F. Rols**  
- Memberships: owner / admin / member (ja implementat + protecció darrer owner).  
- Platform: `platform_roles.superadmin` (seed inicial manual o via migració controlada).  
- Frontend: `canManage = memberships.some(m => m.role in ['owner','admin'] && m.slug === actorId)`.
