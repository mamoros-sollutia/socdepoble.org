# PART 1 · PURGA SQL DELS PERFILS ZOMBIS

## ⚠️ SDP-LOCK ACTIU

Operació destructiva encàrregada pel responsable (el Mestre). Protocol: **previsualitzar → backup → transacció amb porta de 3 files**. Base legal: neteja de dades de prova, registres sense valor personal (`username IS NULL`, absents d'`auth.users`).

## 1.1 Per què van quedar orfes (breu)

Esborrar un usuari des del Dashboard (Authentication) esborra **només** la fila a `auth.users`: l'esquema `auth` pertany a GoTrue (`supabase_auth_admin`) i cap procés toca el teu `public`. Si `public.profiles` no declara `FOREIGN KEY (id) REFERENCES auth.users(id) ON DELETE CASCADE` (ni trigger d'esborrat), el perfil queda viu sense ànima: **orfe**. La firma `username IS NULL` és la típica dels comptes de prova.

## 1.2 Script (Supabase Studio · SQL Editor)

> El Studio corre com `postgres` (propietari de `public.profiles`) → bypassa RLS llevat de `FORCE`. El `SET LOCAL` cobrix eixe cas. **Mai** executes això des del client: `anon`/`authenticated` no poden llegir `auth.users`.

```sql
-- ════════════════════════════════════════════════════════════
-- SDP · PURGA PROFILES ORFES · executar al Studio, sencer
-- Precondició: esperat EXACTAMENT 3 files. Si no, ATURA'T.
-- ════════════════════════════════════════════════════════════

-- PAS 1 · PREVIEW (només lectura)
SELECT p.id, p.username, p.full_name, p.created_at
FROM public.profiles AS p
WHERE p.username IS NULL
  AND NOT EXISTS (SELECT 1 FROM auth.users AS u WHERE u.id = p.id);
-- ✔ Verifica: 3 files. Si no → STOP i investiga.

-- PAS 2 · BACKUP reversible
CREATE TABLE public._bk_profiles_orfes_260906 AS
SELECT p.*
FROM public.profiles AS p
WHERE p.username IS NULL
  AND NOT EXISTS (SELECT 1 FROM auth.users AS u WHERE u.id = p.id);

ALTER TABLE public._bk_profiles_orfes_260906 ENABLE ROW LEVEL SECURITY;
-- sense polítiques → només el propietari (Studio) pot llegir-ho

-- PAS 3 · PURGA transaccional
BEGIN;
SET LOCAL row_security = off;  -- vàlid per al propietari de la taula

DELETE FROM public.profiles AS p
WHERE p.username IS NULL
  AND NOT EXISTS (SELECT 1 FROM auth.users AS u WHERE u.id = p.id)
RETURNING p.id;
-- ✔ Si el RETURNING no llista exactament 3 files → ROLLBACK.

COMMIT;

-- PAS 4 · (dies després de validar-ho tot)
-- DROP TABLE public._bk_profiles_orfes_260906;
```

**Doble condició = seguretat:** un perfil legítim amb `username NULL` però amb usuari viu a `auth.users` queda protegit pel `NOT EXISTS`.

## 1.3 Vacuna (que no torne a passar)

```sql
ALTER TABLE public.profiles
  DROP CONSTRAINT IF EXISTS profiles_id_fkey;

ALTER TABLE public.profiles
  ADD CONSTRAINT profiles_id_fkey
  FOREIGN KEY (id) REFERENCES auth.users (id) ON DELETE CASCADE;
```

Nota: és el patró documentat de Supabase ("Managing User Data"). Caveat menor: una FK cap a `auth` pot alterar l'ordre d'objectes en restauracions `pg_dump`; si molesta, l'alternativa és un trigger `AFTER DELETE ON auth.users` que purgue el perfil.

# PART 2 · ARQUITECTURA: PERSONA vs ENTITAT

## 2.1 Principis

1. `auth.uid()` és la identitat **tècnica** (una per humà). Persona i Entitat són identitats **socials**: el mateix humà, diferents barrets.
2. Tota fila de contingut té un **propietari explícit i únic** (restricció XOR).
3. Moure ≠ copiar: les transferències són `UPDATE` de propietat. Una sola font de veritat (Online-First, [[ADR-2026-08-ONLINE-FIRST]]).
4. RLS és el guàrdia; el client només demana.
5. Zero dependències noves, zero Tailwind.

## 2.2 Decisió de model (mini-ADR)

| Opció | Veredicte |
|---|---|
| Polimòrfica (`owner_type` + `owner_id`) | ✖ Cap integritat FK, RLS dolorosa |
| Taula unificada `actors` | ✖ Indirecció i migració pesada; possible evolució futura |
| **Doble FK amb XOR** | ✔ Integritat referencial, RLS directa, transferència = UPDATE |

Registra-ho com `ADR-2026-09-IDENTITAT-PERSONA-ENTITAT.md`.

## 2.3 Esquema de dades

```sql
-- ENTITATS (Empresa o Grup)
CREATE TABLE public.entities (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug        text NOT NULL UNIQUE,
  name        text NOT NULL,
  kind        text NOT NULL CHECK (kind IN ('empresa', 'grup')),
  description text,
  logo_url    text,
  created_by  uuid REFERENCES public.profiles (id) ON DELETE SET NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

-- MEMBRESIA Persona ↔ Entitat (N:M amb rol)
CREATE TABLE public.entity_members (
  entity_id  uuid NOT NULL REFERENCES public.entities  (id) ON DELETE CASCADE,
  profile_id uuid NOT NULL REFERENCES public.profiles (id) ON DELETE CASCADE,
  role       text NOT NULL DEFAULT 'member'
             CHECK (role IN ('owner', 'admin', 'member')),
  joined_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (entity_id, profile_id)
);

-- PROPIETAT DEL CONTINGUT (patró per a CADA taula de contingut:
-- notes, mercat, mur, multimedia... — ací "notes" com a exemple)
ALTER TABLE public.notes
  ADD COLUMN owner_profile_id uuid REFERENCES public.profiles (id) ON DELETE CASCADE,
  ADD COLUMN owner_entity_id  uuid REFERENCES public.entities  (id) ON DELETE CASCADE;

-- Backfill: el contingut existent pertany al seu autor personal
-- (<autor_actual> = la columna d'autoria ja existent de cada taula)
UPDATE public.notes SET owner_profile_id = <autor_actual>
WHERE owner_profile_id IS NULL AND owner_entity_id IS NULL;

ALTER TABLE public.notes
  ADD CONSTRAINT notes_owner_xor CHECK (
    ((owner_profile_id IS NULL) <> (owner_entity_id IS NULL)) OR (owner_profile_id IS NULL AND owner_entity_id IS NULL)
  );
```

> Decisió de governança: `ON DELETE CASCADE` a la propietat = si mor un perfil, marxa el seu contingut personal. Si voleu conservar-ho, `SET NULL` + neteja diferida.

## 2.4 RLS — helpers i polítiques canòniques

```sql
-- Helpers (SECURITY DEFINER evita recursió de polítiques)
CREATE FUNCTION public.sdp_es_membre_entitat(p_entity uuid)
RETURNS boolean LANGUAGE sql STABLE
SECURITY DEFINER SET search_path = public AS $$
  SELECT EXISTS (SELECT 1 FROM public.entity_members
    WHERE entity_id = p_entity AND profile_id = auth.uid());
$$;

CREATE FUNCTION public.sdp_es_admin_entitat(p_entity uuid)
RETURNS boolean LANGUAGE sql STABLE
SECURITY DEFINER SET search_path = public AS $$
  SELECT EXISTS (SELECT 1 FROM public.entity_members
    WHERE entity_id = p_entity AND profile_id = auth.uid()
      AND role IN ('owner', 'admin'));
$$;

-- Polítiques per taula de contingut (exemple: notes)
ALTER TABLE public.notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY notes_read ON public.notes FOR SELECT USING (
  owner_profile_id = auth.uid()
  OR public.sdp_es_membre_entitat(owner_entity_id)
);

CREATE POLICY notes_insert ON public.notes FOR INSERT WITH CHECK (
  owner_profile_id = auth.uid()
  OR public.sdp_es_admin_entitat(owner_entity_id)
);

-- UPDATE = la clau de les transferències:
-- USING  → qui pot TOCAR la fila (propietari actual)
-- WITH CHECK → qui pot SER el destí (admin de l'entitat receptora)
CREATE POLICY notes_update ON public.notes FOR UPDATE
  USING (
    owner_profile_id = auth.uid()
    OR public.sdp_es_admin_entitat(owner_entity_id)
  )
  WITH CHECK (
    owner_profile_id = auth.uid()
    OR public.sdp_es_admin_entitat(owner_entity_id)
  );

CREATE POLICY notes_delete ON public.notes FOR DELETE USING (
  owner_profile_id = auth.uid()
  OR public.sdp_es_admin_entitat(owner_entity_id)
);
```

## 2.5 Matriu de transferència ("passar lliurement")

| Origen | Destí | Qui pot | Mecanisme |
|---|---|---|---|
| Personal | Entitat | admin/owner de l'entitat destí | `UPDATE` XOR |
| Entitat | Personal | admin/owner de l'entitat origen | `UPDATE` XOR |
| Entitat | Entitat | admin/owner en ambdues | `UPDATE` XOR |

```sql
-- Exemple: donar una nota personal a una entitat
UPDATE public.notes
SET owner_profile_id = NULL, owner_entity_id = :entity_id
WHERE id = :note_id;  -- RLS valida tot server-side
```

## 2.6 Descomposició React de `AppDataContext.jsx`

```
src/app/
├── AppDataProvider.jsx                 ← compositor: munta l'arbre, res més
├── auth/SessionContext.jsx             ← sessió GoTrue + client Supabase
├── identity/ProfileContext.jsx         ← perfil personal
├── identity/EntitiesContext.jsx        ← entitats, membres, rols
├── identity/ActiveIdentityContext.jsx  ← el barret en ús (persona O entitat)
└── data/<domini>Context.jsx            ← Notes, Mercat, Mur… filtrats per identitat
```

| Context | Consumix | Estat | Accions |
|---|---|---|---|
| `SessionContext` | — | `session, ready` | `signIn, signOut, supabase` |
| `ProfileContext` | Session | `profile` | `updateProfile` |
| `EntitiesContext` | Session | `entities[], roles` | `createEntity, addMember, setRole` |
| `ActiveIdentityContext` | Profile+Entities | `identity, canAdmin` | `setPersonal, setEntity` |
| `DomainContext` (N) | ActiveIdentity | `items[]` filtrats | CRUD + `transfer(id, target)` |

**Regles:**

1. **Jerarquia unidireccional:** cada context només consumix el pare immediat.
2. `ActiveIdentity` és un valor opac per als dominis — no saben si parlen amb persona o entitat:
```js
// shape
{ type: 'profile' | 'entity', id, label, avatar, canAdmin }
// helper únic: src/lib/ownership.js
const ownerFilter = (i) => i.type === 'entity'
  ? { owner_entity_id: i.id } : { owner_profile_id: i.id };
```
3. **Transferència des del domini** (RLS fa de guàrdia):
```js
async function transferNote(noteId, target) {
  const patch = target.type === 'entity'
    ? { owner_profile_id: null, owner_entity_id: target.id }
    : { owner_profile_id: target.id, owner_entity_id: null };
  const { error } = await supabase.from('notes').update(patch).eq('id', noteId);
  if (!error) await supabase.from('ownership_transfers').insert({ /*…*/ });
  refresh();
}
```
4. **Persistència del barret actiu:** `localStorage` (`sdp.activeIdentity`). És estat d'interfície, NO dada → l'Online-First queda intacte: tota la informació sempre ve de Supabase.
5. **Precedent:** `src/sections/notes/NotesContext.jsx` ja és un context de domini → replicar el patró per secció.
6. **Migració sense big-bang:** `AppDataContext.jsx` es converteix en *facade* que reexporta dels contexts nous; s'esborra quan tots els consumidors estiguen migrats.
7. Zero llibreries noves: Context + hooks + el client Supabase existent.

## 2.7 Sollutia

Sollutia es materialitza com la primera `entity` (`kind: 'empresa'`), amb el Mestre com a `owner`. La "connexió perfecta" amb el seu sistema queda dins del model sense cap cas especial.
