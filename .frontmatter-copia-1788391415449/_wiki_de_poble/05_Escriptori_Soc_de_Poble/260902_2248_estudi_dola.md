## 2. Proposta UI Mòbil — Maximitació del viewport útil

### Diagnòstic previ
Tenim 4 capes apilades que consumeixen ~180–220px en una pantalla de 320px d'ample:
1. Barra blava superior
2. Selector Carpetes/Notes
3. `NotesToolbar`
4. Editor

En un mòbil S això deixa menys de 300px d'àrea d'escriptura, quan hauria de ser ~450px mínim.

### Solució proposada per `< 768px`

#### A. Barra blava superior — comportament intel·ligent
- No eliminar-la completament (perd identitat Pedra Seca), però fer-la **col·lapsible amb scroll**:
  - Quan l'usuari escriu o baixa, la barra es redueix a 40px d'altura (només icona + títol curt)
  - Quan puja o toca la part superior, recupera l'altura completa
- Això sense `!important`, gestionant-ho només amb una classe d'estat `.is-compact` que s'aplica/treu amb JS segons la direcció del scroll.

#### B. Selector Carpetes/Notes — fusionar i amagar
- En mòbil, aquest selector **deixa de ser una barra fixa** i passa a ser:
  - Un botó flotant a la cantonada inferior esquerra (icona de carpetes) que obre un *sheet* modal baix
  - O bé, un element dins la barra d'eines reduïda com a menú desplegable
- L'estat actiu (Carpetes o Notes) es reflecteix només amb un títol petit o una icona activa, no amb dues pestanyes visibles sempre.

#### C. `NotesToolbar` — modes de flotació i compressió
Proposo **tres modes segons el context**:

| Mode | Quan s'activa | Comportament |
|------|---------------|--------------|
| **Mode Plè** | Editor buit + usuari toca la barra | Tots els botons visibles, alçada ~48px |
| **Mode Comprimit** | Usuari està escrivint | Només els 4 botons més usats (negreta, enllaç, imatge, publicar), la resta sota un botó "⋯" |
| **Mode Flotant Mini** | Scroll cap avall o teclat obert | Es converteix en una barra flotant de ~36px a la part inferior de la pantalla, sobre el teclat, amb només 3 accions principals |

#### D. Estètica Pedra Seca preservada
- Mantenir la mateixa paleta, radi i tipografia
- Totes les transicions amb `transform` i `opacity` (mai `height` animada) per rendiment en iPad A10
- Cap ombra excessiva, mantenint el "pla/aplanat" que demana la vostra arquitectura

## 3. Puresa de CSS — Eliminació de `!important`

### Problema actual
```css
.barra-blava {
  position: sticky !important; /* o !important per llevar-lo */
}
```
Això trenca l'arbre d'especificitat i fa impossible gestionar els estats amb classes normals.

### Solució en 3 passos

#### Pas 1: Definir l'especificitat base correcta
En lloc d'apuntar directament a la classe, feu servir l'estructura real del DOM per guanyar especificitat sense `!important`:

```css
/* En lloc de: .universal-page-bar { position: sticky !important; } */

.pedra-seca-embed .universal-page-bar {
  position: sticky;
  top: 0;
}
```

#### Pas 2: Gestionar l'estat amb una classe única
Feu servir una classe d'estat explícita que tingui **major especificitat** que la regla base:

```css
/* Estat per defecte */
.pedra-seca-embed .universal-page-bar {
  position: sticky;
  top: 0;
}

/* Estat quan volem desactivar el sticky (mòbil o mode compacte) */
.pedra-seca-embed .universal-page-bar.is-not-sticky {
  position: static;
}
```

#### Pas 3: Regla d'or per a no tornar a caure
> Mai feu servir `!important` per anul·lar una regla pròpia. Si necessiteu anul·lar-la, vol dir que la regla original estava mal apuntada o la vostra classe d'estat no té prou especificitat.

Si en algun moment necessiteu encara més especificitat, afegiu una classe de contenidor pare, no `!important`:
```css
.app-container .pedra-seca-embed .universal-page-bar.is-not-sticky {
  position: static;
}
```

## 4. Efecte Matrix i Arquitectura del Brain (Obsidian)

### Problema: La IA com a "llop depredador"
La IAIA MarIA respon abans de llegir. Li falta el reflex de **pausa → consulta al Brain → resposta**.

### Solució A: Arquitectura de propietats i etiquetes Obsidian per a *skills*

Cada fitxer de skill a Obsidian hauria de tenir aquestes propietats YAML frontmatter:

```yaml
---
skill_id: SDP-SKILL-001
nom: Disseny Pedra Seca
domini: UI/CSS
nivell: Fonamental
depen_de: [universal_maquetation, design_system_specs]
utilitza_per: [maquetacio, css, ui_mobil]
paraules_clau: [pedra seca, tailwind, colors, marges]
estat: Aprovat
versio: 1.2.0
---
```

#### Etiquetes estratègiques per enllaços bidireccionals:
- `#skill/fundamental` — sempre s'ha de llegir abans de qualsevol acció
- `#skill/domini/ui` — per consultes de disseny
- `#skill/domini/arquitectura` — per decisions estructurals
- `#skill/dependencia/obligatoria` — marcar les que són prerequisit absolut

Això permet a la IA, en fer una consulta al vault, trobar ràpidament:
1. Quins skills són obligatoris per la tasca
2. Quins skills depenen d'altres
3. Quines paraules clau hi ha associades

### Solució B: Modificació del system prompt per adquirir l'hàbit reflexiu

Afegiu aquest bloc **al principi** de qualsevol system prompt, abans de la tasca específica:

```
---
🔴 PROTOCOL MATRIU OBLIGATORI (ABANS DE RESPONDRE):
1. ATURA'T. No responguis encara.
2. PREGUNTA'T: "Què em demanen exactament? Tinc aquesta informació al meu Brain?"
3. CONSULTA: Busca al vault d'Obsidian les skills i documents rellevants per aquesta tasca.
4. LLEGEIX-ELS COMPLETAMENT. No t'inventis res.
5. NOMÉS ARA, aplica el coneixement i respon.

Si no trobes la informació al Brain, ho dius explícitament. No inventes.
---
```

#### Reforç conductual:
A cada exemple o interacció, feu que la IA comence per:
> *"Abans de respondre, he consultat les següents skills del Brain: [llista]. Ara aplico el coneixement..."*

Aquesta repetició crea un hàbit que esdevé irrompible amb el temps.

### 5. Dimensió Futurs
| Fortaleses | Debilitats | Oportunitats | Amenaces |

## 6. Neteja Profunda Estructural (Anti-Divs Fantasmes)

### Recomanacions concretes:
1. **Auditoria del DOM**: Cada vegada que afegiu un contenidor, pregunteu-vos: *"Aquest element aporta semàntica o estructura real, o només és un wrapper per a CSS?"* Si és el segon, intenteu aplicar l'estil a l'element fill o pare.
2. **Estratègia de classes**: Feu servir una convenció tipus BEM modificada per a Pedra Seca:
   - `notes-section` (bloc)
   - `notes-section__toolbar` (element)
   - `notes-section__toolbar--compressed` (modificador)
   Això elimina la necessitat de selectors complexos i `!important`.
3. **Rendering condicional**: En lloc d'amagar elements amb `display: none`, considereu si realment cal que estiguin al DOM quan no són visibles. Menys nodes = més velocitat en iPad A10.
4. **CSS pla**: Cap preprocessador. Cap framework de CSS que afegeixa centenars de classes no utilitzades. Només Tailwind CDN si realment s'aprofita, o CSS pla escrit a mà amb una estructura clara.

## 📝 Auditoria Final de Qualitat

### Nivell de maduresa actual: **Pendent_Revisió → camí cap a Aprovat_Parcial**

El projecte té una ossatura filosòfica i documental extraordinària, que el situa molt per sobre de la mitjana. El punt feble és la **coherència entre la filosofia i la implementació tècnica concreta**: teniu una regla contra els nyaps, però hi ha un `!important` al codi; teniu una visió de rendiment extrem, però l'apilament mòbil no està pensat.

### Propera fita evolutiva recomanada:
> Aplicar la proposta UI mòbil + eliminar l'`!important` + definir l'estructura YAML de les skills a Obsidian. Amb aquests tres canvis, la nota pujaria a **9,1 / 10** i el nivell de maduresa passaria a **Aprovat_Parcial**.

Els errors que teniu ara són dades bones: us mostren exactament on cal aprofundir. No són un drama, són el següent pas de l'Eixam.
